# Zero-waste infrastructure: first implementation pass

The existing Founding 20 integration is already complete and there are now 25 designs. This pass prioritises the proposal’s media extraction and Supabase query work; it does not claim that every infrastructure milestone has been deployed.

Source totals come from `media-extraction-report.json`. The original/default image totals differ in scope because the optimised set also contains imported stock imagery; they are not a like-for-like compression ratio. Multiple responsive variants increase static storage to approximately 22 MB. These are Cloudflare/GitHub files, not Supabase customer storage.

Cold-cache browser tests at 390 CSS pixels and DPR 2 measured first-screen static transfers of about 61–492 KB across all 25 previews. This excludes external fonts, backend responses, browser overhead, subsequent interactions and scrolling. It is a reproducible local static-assets measurement, not a production Core Web Vitals or billable-egress result. Four detailed cover images are retained at 100–136 KB rather than aggressively reducing quality. Largest 1920px high-detail images intentionally exceed the suggested 350 KB hero target; the default 960px images do not. Do not describe the initial-load target as universally guaranteed.

## Media delivery

- All twenty-five shared interiors are in `templates/001.html` through `templates/025.html`. Preview shells and the guest viewer fetch them; rendered websites are not stored per customer.
- Embedded photographic data is extracted into deduplicated WebP files with 320/640/960/1440/1920px variants where the original supports those widths. Smaller originals are not upscaled.
- Responsive `srcset`/`sizes` and lazy loading cover static image markup. Native dynamically generated galleries keep functional defaults, with lazy-loading hints where appropriate. CSS photographic backgrounds select mobile/tablet/desktop variants without changing their gradients, crop positions or animations.
- Inline native CSS and JS are externalised to content-fingerprinted files. The body structure, text, IDs and interactive controls of all 25 designs are checked against approved commit `c4f8b13` by `scripts/check-template-structure.py`.
- Explicit owner photograph overrides remain supported. Speculative requests for non-existent local image slots and automatic remote Pexels substitutions are removed. File-based overrides use an index generated by the static build; rebuild after adding a local replacement.
- Edited/customer photos clear old responsive defaults so a template `srcset` cannot replace the personal photograph.
- Owner-selected collection videos retain posters and are not requested until near the viewport; reduced-motion users retain still artwork.

## Customer uploads

The builder accepts up to 12 photographs. A shared browser encoder targets a maximum of 300 KiB per new uploaded image, with WebP and JPEG canvas fallback. It starts at a 1600px longest edge and high quality, then reduces size/quality as needed; originals are not uploaded by this flow. Tap-to-edit and final cloud save use the same encoder. Cloud-save paths use encoded content hashes and reuse files on repeated uploads; scoped private paths and existing customer photographs are preserved.

A pre-save check counts distinct personal photo sources across gallery and edited slots. This is a browser-side product limit, not a server-side quota guarantee. Storage bucket limits and server-side per-invitation enforcement remain a further hardening step. No abandoned drafts or published invitations were deleted; no retention policy was silently introduced.

New invitation inserts contain compact text edits, not temporary base64 photo payloads. Existing saved references continue to load. Existing objects are not recompressed or deleted in place.

## Supabase

- The private dashboard fetches 50 compact summaries at a time, including names/date JSON projections. It fetches full event/design data only for editing or sharing a selected event. The overview/search describe the loaded invitations; “Show older invitations” expands them.
- The public endpoint remains published-only and whitelists event fields and edits. Guest contact/reply records are never included.
- All valid private photo paths are deduplicated and signed with one `createSignedUrls` call, instead of sequential per-image signing requests. Batch errors are not cached as successful invitations.
- Public data remains `no-store` until a Cloudflare cache with a tested edit/unpublish invalidation path exists. No private dashboard, session or RSVP response was put in a public cache.
- Existing slug, owner, RSVP invitation and duplicate-email indexes were inspected. No speculative indexes or RLS weakening were added. The current small dataset did not warrant another index.
- Read-only SQL initially measured 5 invitation rows, maximum event JSON 413 bytes, maximum design JSON 388 bytes and about 12 MB database size. This is a snapshot, not an egress or storage-plan reading. `scripts/usage-report.sql` reports aggregate data without guest contact details; monthly egress/build usage still comes from provider dashboards.

## Build and Cloudflare handoff

Run `python scripts/build-static.py`; publish `dist` from a Cloudflare Pages project connected to the repository. It uses Python’s standard library; image conversion is already committed. The build regenerates the local replacement index, excludes Git/developer/server files, and rejects a file of 25 MiB or more or 20,000 files or more. `_headers` provides immutable caching only for content-fingerprinted media/code, revalidation for template documents and no-store on private entry pages.

The Cloudflare connector returned an authentication-request loop on both attempts. No Cloudflare account deployment or free hostname was verified, and the working GitHub deployment is retained. Before switching the public origin, reconnect the account, create/verify a preview deployment, add its exact approved origin to existing checkout/publish/RSVP allowlists, configure Supabase Auth redirect URLs, and verify every customer flow. Do not allow arbitrary `*.pages.dev` origins. Canonical and social URLs remain on the verified GitHub host until the new hostname is known.

To regenerate the one-time extraction, use Pillow with WebP support and run `python scripts/extract-template-media.py --remote`, then `python scripts/fingerprint-media.py`, update the cover variants if their originals changed, and run the checks. The extraction’s pinned approved source protects against accidental use of an older ZIP. `fingerprint-media.py` fingerprints served bytes, so an encoder change receives a new immutable URL.

## Remaining proposed milestones

- A verified Cloudflare deployment and end-to-end origin cutover.
- Public metadata edge caching with tested edit/unpublish invalidation, and cache-hit measurements.
- Server-enforced upload quotas, agreed draft retention and reviewed orphan cleanup. Published invitations must not be deleted to fit a free allowance.
- Automated encrypted off-platform backups with a configured destination/key and a tested restore; none was scheduled without those prerequisites.
- Verified transactional authentication email delivery, password-reset recovery and operational monitoring. Domain/email configuration is still required.
- Review existing webhook idempotency and failure recovery under replay/load; test mode and prices are unchanged.
- Provider usage alerts and actual cached/uncached egress/build monitoring. Static size estimates do not establish free-tier safety.

No new paid service, R2 migration, synthetic keepalive activity or payment-mode switch was introduced. Free hosting remains a target, not a reliability or cost guarantee.
